# Plan First（先报批，后动手）

> Approval-gated execution for AI assistants: stay read-only and keep planning until the user explicitly says **开干** (go).

一个给 AI 助手用的 skill：**在你亲口说"开干"之前，它只出方案、不动手。**

## 它解决什么问题

AI 助手太急着干活：你说"帮我做个 X"，它可能直接开始写文件 —— 等你发现方向不对，东西已经落盘了。

这个 skill 把流程改成：

```
目标 →【只读出方案】→ 你拍板 → 你说"开干" →【执行】→ 交付 → 你验收
                                            └─ 有意见 → 回炉改方案 → 再等"开干" ↺
```

## 三个档位

| 档位 | 什么要报批、给多细 | 动工口令 | 自我约束 |
|---|---|---|---|
| 严格档 | 任何改动都要报批；每轮给完整八项 | 只有"开干" | 3、4、5、6 |
| 正常档 | 任何改动都要报批；首轮完整，之后只写改动处 | 只有"开干" | 3、5 |
| 信任档 | 只有大事要报批；大事给完整八项，小事直接做 | 小事免口令；大事只有"开干" | 无 |

编号见「六条干活原则」。

第一次出方案时，助手会问你选哪一档。

## 唯一的口令

严格档和正常档下，**只有"开干"两个字算数**：

- **算**：`开干`
- **不算**："可以"、"同意"、"批准"、"全部默认"、"就按你说的办"、"看起来不错"、回答了拍板问题、只夸方案

不是"开干"，助手只会回你一句："如果确认开工，请回复'开干'。"

而且**一次"开干"只管一次** —— 方案改一版，上一句就作废。

## 六条干活原则

动手之后别骗自己 —— 这六条写进 skill 里，按档位决定详略：

1. **先说清"怎么算失败"**：动手前写一句 —— 出现什么现象就算没做成。
2. **计划可以改，但改动要留痕**：原以为 → 实际是 → 所以改为。
3. **证据要能自证**：先确认你的检查工具查得出问题，再信它说的"没问题"。
4. **卡住就上报**：同一处调两三次还不通，停下来说清卡在哪、需要什么。
5. **共用的东西指定唯一负责人**：谁写、资源归谁、谁都不许单方面打断别人。
6. **留退路**：重大改动前记下怎么退回去；坏了先回滚，别在坏的东西上继续修。

## 安装

整个 skill 就是一个 `SKILL.md`。放进宿主扫描的 skill 根目录即可，两种都行：

- **项目级**：`<你的项目>/.dsh/skills/plan-first/SKILL.md`
- **用户级**：`~/.dsh/skills/plan-first/SKILL.md`（所有项目可用）

两个常见的坑：

1. **只发现扫描根目录顶层的 `<name>/SKILL.md`，嵌套的 `**/SKILL.md` 故意不认。** 别放成 `skills/some-collection/plan-first/SKILL.md`。
2. 目录名与 frontmatter 里的 `name` 保持一致，省得排查。

放好之后**不需要重启**：支持文件系统 skill 的宿主会自己刷新技能目录。

> 路径按宿主而定，上面是 DSH 的约定；任何支持 `SKILL.md` + YAML frontmatter 的宿主都能用这个 skill。

## 用法

- **自动**：你提出"给我做个 X / 帮我改成 Y / 你先出方案"这类目标时，助手应当自己加载它。
- **手动**：发一个 `/plan-first`（前后有空格）强制注入全文，不经过助手的判断。

## 已知局限

- 它是**软约束**：靠助手照它执行，宿主不会物理拦截。要硬拦截（没批准就写不了文件），得把会话权限设成只读（read-only）。
- 口令**只对当次有效**，不跨对话继承。

## 由来

六条干活原则是从一次真实的调试会话里蒸馏出来的 —— 那轮把文中列的那些错基本都犯了一遍，包括反复报"验证通过"、反复被打脸。
